# AI-помощник по обработке заявок

Небольшое веб-приложение: вставляете текст заявки — получаете готовую карточку лида
для менеджера (тип лида, известные данные, чего не хватает, следующий шаг и черновик ответа).

Приложение работает локально на вашем компьютере. Никакой базы данных, CRM и регистрации.

---

## Что нужно для запуска

**Python версии 3.9 или новее.** Скорее всего, он уже установлен.

Проверить можно одной командой в Терминале:

```bash
python3 --version
```

Если видите версию вида `3.11.12` — всё в порядке.
Если пишет «command not found», скачайте Python с [python.org](https://www.python.org/downloads/)
(кнопка «Download Python 3» на главной странице) и повторите.

Больше ничего ставить не нужно. Все библиотеки приложение поставит само при первом запуске.

## Быстрый старт (3 шага)

### Шаг 1. Получите ключ ProxyAPI

1. Откройте [console.proxyapi.ru](https://console.proxyapi.ru) и зарегистрируйтесь (нужна почта).
2. Подтвердите почту по ссылку из письма.
3. Зайдите в раздел **«Ключи API»** и нажмите «Создать ключ».
4. Скопируйте ключ — он выглядит так: `sk-xxxxxxxxxxxxxxxxxxxx`.
   **Ключ показывают только один раз** — сохраните его сразу.
5. Пополните баланс в разделе **«Биллинг»** (нужна карта российского банка). Без денег на балансе
   запросы работать не будут.

### Шаг 2. Впишите ключ в файл `.env`

Файл `.env` уже создан в папке проекта — это обычный текстовый файл с настройками.
Откройте его двойным кликом (если открылся не TextEdit, а другая программа — правый клик →
«Открыть в программе» → TextEdit) и впишите ключ:

```
PROXY_API_KEY=sk-ваш_ключ_сюда
PROXY_API_BASE_URL=https://api.proxyapi.ru/v1
OPENAI_MODEL=openai/gpt-5-mini
PORT=8000
COMPANY_DESCRIPTION=Продаём CRM-систему и техническую поддержку для B2B-компаний.
```

Важны только две строки:

- `PROXY_API_KEY` — сюда вставляете ключ;
- `COMPANY_DESCRIPTION` — 1–2 предложения о том, **что продаёт ваша компания**.
  Без этого описания помощник хуже понимает, какие заявки относятся к вам, а какие нет.

Остальные строки можно не трогать.

> Если файла `.env` потерялся, создайте его заново одной командой в папке проекта:
> `cp .env.example .env`

### Шаг 3. Запустите приложение

**Способ 1 (проще).** Дважды кликните по файлу **`start.command`** в папке проекта.
Откроется окно Терминала, приложение само поставит библиотеки, запустится и откроет
браузер с готовой страницей.

**Способ 2 (через Makefile).** Откройте Терминал в папке проекта и выполните:

```bash
make run
```

Команда сама создаст виртуальное окружение (если его ещё нет), поставит библиотеки
и запустит приложение. Остановить — **Ctrl + C** в этом же окне.
Другие команды: `make setup` (только подготовить окружение), `make clean` (убрать кэши),
`make help` (список команд).

**Способ 3 (вручную).** В Терминале в папке проекта выполните 4 команды по очереди:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

После последней команды в браузере откройте **http://127.0.0.1:8000**
(при первом запуске скрипт откроет браузер сам).

### Как выключить

В окне Терминала нажмите **Ctrl + C**. Если запускали двойным кликом по `start.command` —
закройте это окно Терминала.

### Если порт занят

Приложение по умолчанию использует порт **8000** (`PORT=8000` в `.env`).
Порты 3000 и 5000 на многих компьютерах уже заняты — например, порт 3000 часто занимает
контейнер Docker с браузером для автотестов.

Если порт из `.env` занят, приложение **не падает, а само переключается на свободный порт**
и пишет об этом в окне Терминала:

```
Порт 3000 занят другой программой (это может быть контейнер Docker или другое приложение).
Приложение запущено на свободном порту 3001.
```

В этом случае открывайте именно тот адрес, который написан в окне Терминала.
Текущий порт также лежит в файле `.port` рядом с `app.py`.

> Почему нельзя просто открыть `localhost:8000`, если заняты другие порты:
> `localhost` сначала пробует IPv6-адрес `::1`, и если там кто-то слушает — запрос уходит
> чужой программе. Поэтому всегда открывайте адрес из окна Терминала — `127.0.0.1:<порт>`.
> Скрипт `start.command` открывает в браузере именно его.

## Как пользоваться

Заполните форму и нажмите **«Обработать»**:

| Поле | Обязательное | Что это |
|---|---|---|
| **Имя** | нет | Имя контактного лица — попадёт в «Известные данные» |
| **Телефон** | нет | Контактный телефон клиента |
| **Почта** | нет | Электронная почта клиента |
| **Заявка** | **да** | Сам текст обращения: что нужно, сколько, на каких условиях |

Контактные поля необязательны, но с ними карточка получается точнее. Если их не заполнить,
в «Известных данных» будет «не указано», а «контакт» попадёт в список «чего не хватает».

Обработка занимает примерно 10–15 секунд. Пока идёт разбор, рядом с кнопкой
тикает счётчик секунд. Сколько всего заняло — показывается в карточке справа:
«Обработка заняла 9 с · AI 8 с · Битрикс24 1 с». Если запрос завершился ошибкой,
время ожидания тоже будет показано.

Ниже появится карточка — кнопки «Копировать карточку» и «Копировать ответ» копируют
текст в буфер обмена.

Что компания продаёт, приложение берёт из файла `.env` (строка `COMPANY_DESCRIPTION`) —
менять это на странице не нужно. Если описание не задано, сверху появится напоминание.

**Ctrl + Enter** (на Mac — **Cmd + Enter**) в поле «Заявка» отправляет форму не нажимая кнопку.

Галочка **«Отправить в Битрикс24»** (включена по умолчанию) отправляет готовую карточку
в CRM. Подробности — в разделе «Интеграция с Битрикс24 CRM».

## Что есть в карточке

| Поле | Что означает |
|---|---|
| **Тип лида** | `целевой` (про наш товар и понятно, что предлагать), `нецелевой` (не про наш продукт), `неясно` (данных или конкретики мало) |
| **Почему такой тип лида** | Короткое объяснение выбора — видно, на чём основан вывод |
| **Компания** | Название компании из текста заявки |
| **Суть запроса** | 1–2 предложения о том, чего хочет клиент |
| **Известные данные** | 7 полей: компания, имя, контакт, продукт, количество, бюджет, сроки. Если данных нет — «не указано» |
| **Чего не хватает** | Важные данные, которых нет в заявке |
| **Уточняющие вопросы** | 1–2 вопроса клиенту, когда информации не хватает |
| **Следующий шаг** | Что конкретно сделать менеджеру |
| **Причина передачи человеку** | Почему заявка попала к живому менеджеру |
| **Черновик ответа** | Готовый текст ответа клиенту без неподтверждённых обещаний |

## Обезличивание персональных данных

Перед отправкой в модель текст заявки очищается от персональных данных: они заменяются
временными токенами вида `[ТЕЛЕФОН_1]`. После ответа модели значения подставляются обратно,
поэтому в карточке менеджер видит настоящие данные.

| Что скрывается | Токен |
|---|---|
| ФИО | `[ИМЯ_1]` |
| Телефон | `[ТЕЛЕФОН_1]` |
| E-mail | `[ПОЧТА_1]` |
| Адрес | `[АДРЕС_1]` |
| ИНН, СНИЛС, паспорт | `[ИНН_1]`, `[СНИЛС_1]`, `[ПАСПОРТ_1]` |
| Банковская карта | `[КАРТА_1]` |
| Дата рождения | `[ДАТА_РОЖДЕНИЯ_1]` |

**Что не скрывается и почему.** Названия компаний, суммы, количества, сроки и названия
товаров — это не персональные данные, и без них модель не сможет определить тип лида и
предмет покупки. Например, «ООО ОфисЛайн» и «500 000 рублей» уходят в модель как есть.

**Где смотреть.** Под полем «Заявка» есть блок «Текст, который уходит в LLM» — он обновляется
по мере ввода и показывает ровно тот текст, который уйдёт в модель, вместе со списком
найденных типов данных («скрыто: имя (2), телефон (1)»). Значения в списке не показываются.

**Где живёт соответствие.** Только в памяти текущего запроса: это локальная переменная,
которая исчезает вместе с ответом. Ничего не пишется на диск, в логи, в модульные переменные
и в базу.

**Регистр и форма имени.** Клиент часто пишет имя с маленькой буквы («меня зовут иван»).
Приложение приводит имена к правильному виду: в «Известных данных» и во всех текстах карточки,
включая черновик ответа. Ориентир — поле «Имя»: «иван петров» станет «Иван Петров». Фамилии при
этом не страдают: «Иванов» останется «Иванов», а слова вроде «марка» — «марка».

**Как обращаться к клиенту.** В черновике ответа — только имя или имя с отчеством:
«Здравствуйте, Мария!» или «Здравствуйте, Пётр Иванович!». Фамилия в обращении не
используется никогда, а форма «Фамилия Имя» («Здравствуйте, Савельева Мария!») — это порядок
для документов, в разговоре он не встречается. Приложение приводит обращение к нужному виду
и в том случае, если модель ошиблась. В поле «Имя» ФИО записывается в привычном порядке:
«Савельева Мария» → «Мария Савельева».

**Чего объяснить нельзя.** Латинское ФИО в свободном тексте (вне полей формы) и описательные
адреса («второй этаж, напротив магазина») остаются как есть. Лексиконы имён и городов расширяемые.

**Как это устроено.** Файл `anonymizer.py` — отдельный модуль без зависимостей от веба и AI:

- сначала заменяются значения, введённые в поля формы (имя, телефон, почта) — во всех
  вхождениях по всему тексту, включая тело заявки;
- затем регулярками ищутся персональные данные в свободном тексте: e-mail, телефоны во всех
  форматах, ФИО, адреса, реквизиты по маркерам, карта, дата рождения;
- имена ищутся по лексикону (около 200 русских и английских имён) **с учётом падежных
  форм**: «меня зовут Анну», «спросить Ивана», «пришлите КП Анне» — тоже находятся.
  Фамилия распознаётся рядом с именем в обе стороны: «Иванов Пётр» и «Пётр Иванов»;
  латинские имена — по словарю английских имён и по контексту («меня зовут John Smith»),
  при этом «Acme Corp» и «Microsoft Office» остаются нетронутыми;
- имя внутри e-mail или телефона отдельно не выделяется: «michael@acme.com» — это один
  контакт, а не имя плюс почта;
- найденные фрагменты, пересекающиеся друг с другом, разрешаются в пользу более приоритетного;
- одинаковые значения получают один и тот же токен, поэтому восстановление однозначно;
- имена сохраняются с большой буквы, даже если клиент написал с маленькой.

**Что модель видит вместо имени.** В системном промпте сказано: токен [ИМЯ_1] — это ФИО
контактного лица, использовать его в ответе ровно как есть, не сокращая и не выбрасывая.
Поэтому настоящее имя подставляет приложение — уже после ответа модели.

Проверки обезличивания: `make test` (файл `test_anonymizer.py`, без внешних зависимостей).

**Честно об ограничениях.** Регулярки не ловут всё: латинское ФИО в свободном тексте
(вне полей формы) и описательные адреса («второй этаж, напротив магазина») остаются как есть.
Лексиконы имён и городов расширяемые.

## Интеграция с Битрикс24 CRM

После обработки заявки карточка уходит в CRM: создаётся **лид**, к нему добавляется
**комментарий** с полной карточкой, менеджеру создаётся **задача** и приходит
**уведомление в чат**.

| Шаг | Метод Битрикс24 | Что передаём |
|---|---|---|
| Лид | `crm.item.add` | компания, ФИО, телефон, почта, бюджет, тип лида, стадия, источник, карточка в комментарии |
| Комментарий | `crm.timeline.comment.add` | полная карточка текстом в таймлайн лида |
| Задача | `tasks.task.add` | следующий шаг в названии, карточка в описании, срок, привязка к лиду. Если нет скоупа `task` — дело «Звонок» в таймлайне лида |
| Уведомление | `im.message.add` | краткая сводка и ссылка на карточку лида |

> Метод `crm.lead.add` в актуальной документации Битрикс24 помечен как устаревший,
> поэтому используется универсальный `crm.item.add` с `entityTypeId: 1` (лид).

### Что нужно настроить в Битрикс24

1. **Входящий вебхук** — CRM → Настройки → Разработчикам → Другое → Входящий вебхук.
   Включите права: **CRM**, **Задачи**, **Чат и уведомления** (im). Скопируйте адрес
   вебхука в `B24_URL`.

   > **Важно про «Задачи».** У раздела задач два скоупа: `task` — актуальный,
   > и `tasks` — устаревший (в документации прямо сказано: «их не нужно использовать»).
   > Методам `tasks.task.add` нужен именно `task`. Если задачи не создаются, а
   > в ошибке mention «не хватает прав» — проверьте, что у вас выдан `task`,
   > а не `tasks`. Кнопка «Проверить Битрикс24» показывает это отдельной строкой.

2. **Ответственный** — `B24_MANAGER_ID`: ID менеджера (его видно в профиле в Битрикс24).
   Если не указать, подставится ID владельца вебхука.
3. **Чат для уведомлений** — `B24_CHAT_ID`: значение из колонки DIALOG_ID в отчёте
   кнопки «Проверить Битрикс24» (например `chat3` для группового чата или `1` для личной
   переписки). Если не указать, уведомления не отправляются — лид и задача создаются.

**Запасной путь.** Если скоупа `task` нет, вместо задачи создаётся дело «Звонок»
в таймлайне лида (ему достаточно уже выданного `crm`). Менеджер всё равно получит
действие, а в блоке CRM будет написано, что создано именно дело.

### Как это работает в приложении

- В форме есть галочка **«Отправить в Битрикс24»** (включена по умолчанию).
  Сняли галочку — карточка обработается, но в CRM ничего не попадёт.
- В карточке появляется блок **«Отправлено в CRM: лид №N»** со ссылкой на карточку лида.
- Если что-то не отправилось (например, недоступны права на задачи) — лид и комментарий
  уже в CRM, а проблема перечислена в блоке. Кнопка **«Повторить отправку»** досылает
  остальное, не вызывая AI повторно.
- **Карточка не теряется никогда:** если Битрикс недоступен, заявка всё равно обрабатывается,
  а в интерфейсе появляется понятное сообщение об ошибке.
- Кнопка **«Проверить Битрикс24»** показывает отчёт: работает ли вебхук, есть ли права
  на CRM и задачи, какие стадии и источники доступны, кто ответственный, какие чаты на выбор.
  Отчёт только читает — ничего не создаёт.

### Настройки `.env`

```
AI_REASONING_EFFORT=low    # насколько модель размышляет: minimal | low | medium | high
B24_URL=https://b24-m2m12u.bitrix24.ru/rest/1/xxxxxxxx/   # адрес входящего вебхука
B24_MANAGER_ID=1        # ответственный (необязательно)
B24_CHAT_ID=chat3       # чат для уведомлений (необязательно)
B24_SOURCE_ID=WEB       # источник лида
B24_CURRENCY_ID=RUB     # валюта суммы
B24_TASK_DAYS=1         # срок задачи в днях
```

### Как карточка попадает в поля лида

| Поле карточки | Поле лида |
|---|---|
| `lead_type` | `stageId`: целевой и неясный → `NEW`, нецелевой → `JUNK` |
| `key_data.company` | `companyTitle` |
| `key_data.name` | `name`, `secondName`, `lastName` (ФИО разбирается по лексикону) |
| `key_data.contact` | `fm`: телефон и почта |
| `key_data.budget` | `opportunity` + `currencyId` (только если сумма однозначна) |
| `lead_type_reason` | `statusDescription` |
| вся карточка | `comments` и комментарий в таймлайне |

Сумма берётся только когда в бюджете одно число: «500 000 - 800 000» — это диапазон,
и подставлять одну из границ значило бы выдумать данные, поэтому поле остаётся пустым.

**Как ФИО попадает в лид.** «Савельева Мария» разбирается на фамилию и имя, в лид уходят
`name: Мария`, `lastName: Савельева`. Если в имени есть отчество, оно идёт в `secondName`.

## Скорость обработки

Обработка заявки — это в основном ожидание модели. Ускорено тремя способами:

1. **`AI_REASONING_EFFORT=low`** — рассуждающие модели (gpt-5, gpt-6) тратят на
   «размышления» до 2000 токенов, и именно они давали основную задержку. Уровень `low`
   сокращает время ответа примерно вдвое без потери точности. Если модель параметр не
   понимает (`gpt-4o-mini`, `gpt-4.1-mini`), приложение повторит запрос без него.
2. **Пакет `batch` для CRM** — комментарий и уведомление уходят одним HTTP-запросом
   вместо двух, задача создаётся параллельно.
3. **Правило про жалобы** в промпте: жалоба по уже сделанной покупке — всегда целевой
   лид. Без этого правила быстрые модели отправляли такие заявки в статус «некачественный».

Замер до и после (ваш портал, ваша модель, реальные заявки):

| | Было | Стало |
|---|---|---|
| Ответ модели | 22,0 с | **9,2 с** |
| CRM (лид, комментарий, задача, уведомление) | 2,0 с | **1,1 с** |
| **Всего на заявку** | **24,1 с** | **10,3 с** |

Диагностика «Проверить Битрикс24» тоже ускорилась: 2,0 с → **0,44 с** (пять проверок
одним пакетом).

Проверить, что точность не просела: `make check-quality` — скрипт прогоняет эталонные
заявки через текущую модель и печатает время и вердикт по каждой. Запускайте его после
любой правки промпта или смены модели.

## Журнал операций

Приложение подробно логирует, что происходит с каждой заявкой и сколько времени занимает
каждый этап. Это нужно, чтобы видеть, где именно тормозит обработка.

В окне Терминала, где запущено приложение:

```
[03:37:17.790] 0001 request.received        Заявка принята | text_len=144, has_name=True, has_phone=True
[03:37:17.791] 0001 anonymize              0.4 ms Персональные данные обезличены | entities=3, text_len=128
[03:37:35.538] 0001 ai.request           17747.0 ms Модель openai/gpt-5-mini ответила | prompt_tokens=2889, completion_tokens=1440
[03:37:35.538] 0001 ai.parse                 0.1 ms Ответ разобран | fields=13
[03:37:35.538] 0001 card.normalize           0.1 ms Ответ приведён к единому виду | lead_type=целевой
[03:37:35.538] 0001 card.guards              0.1 ms Проверены правила квалификации | needs_human=False, missing=2
[03:37:35.539] 0001 card.restore             0.2 ms Возвращены настоящие значения | tokens=3
[03:37:36.130] 0001 b24.call               589.4 ms Метод crm.item.add выполнен | result=item#17
[03:37:37.107] 0001 b24.call               593.9 ms Метод tasks.task.add выполнен | result=task#13
[03:37:37.497] 0001 request.done          19706.9 ms Обработка завершена | ai_s=17.75, crm_s=1.96
```

Что видно сразу: **AI занимает почти всё время** (17,7 с из 19,7 с), а CRM — две сотых.
Если модель отвечает дольше, это первое, что стоит оптимизировать.

Тот же журнал доступен по API — в JSON, с полными данными:

- `GET /api/log?limit=200` — последние записи;
- `DELETE /api/log` — очистить журнал.

**Персональных данных в журнале нет:** записываются только длины текстов, количества
найденных сущений, имена методов, идентификаторы и время. Идентификатор запроса
(`0001`, `0002`…) связывает записи одной заявки — при параллельных запросах не перепутаются.

## Как принимаются решения

Правила зашиты и в промпт (инструкция для AI), и в код (проверка на сервере) — так поведение
предсказуемее.

- **Не выдумываются данные.** Если чего-то нет в тексте заявки — стоит «не указано».
- **Нет обещаний.** Помощник не имеет права писать цену, сроки поставки или скидку,
  если их не было во входном тексте.
- **Жалобы, конфликты, угрозы отказа, требования возврата и нестандартные запросы**
  автоматически помечаются как «нужен человек», даже если AI это пропустил:
  сервер дополнительно проверяет текст заявки по списку признаков.
- **Черновик ответа при передаче человеку** — нейтральный, без обещаний и без «извинений»
  за несуществующие проблемы.

### Как определяется тип лида

AI отвечает на два вопроса **по отдельности**, а итоговое решение принимает сервер —
поэтому правило работает одинаково всегда и его легко поменять в одном месте.

| Вопрос | Что спрашиваем |
|---|---|
| **Предмет** (`subject_match`) | Относится ли запрос к нашим товарам и услугам? Ответ: `да` / `нет` / `неясно` |
| **Определённость** (`offer_clarity`) | Понятно ли, **что именно** мы можем предложить? Ответ: `да` / `нет` |

Правило вывода:

```
предмет = «нет»                      → нецелевой
предмет = «неясно»                   → неясно
предмет = «да», определённость = «нет» → неясно
предмет = «да», определённость = «да» → целевой
```

**Ключевой момент — «определённость».** Запрос считается определённым, если назван
конкретный товар (модель, наименование, артикул) **либо** общий класс товара, но с
конкретными параметрами: количество, бюджет, сроки, назначение, размер, цвет.

Поэтому:

| Заявка | Тип | Почему |
|---|---|---|
| «Сколько у вас стоят офисные кресла? Нужно несколько штук» | **неясно** | Назван только общий класс, нет модели, количества и бюджета — предлагать нечего |
| «Нужно 20 офисных столов и 40 кресел, бюджет 500 000 ₽, до конца месяца» | **целевой** | Класс назван вместе с количеством, бюджетом и сроком — предмет покупки понятен |
| «Кресло Атлант, нужно 10 штук» | **целевой** | Названа конкретная модель и количество |
| «Подскажите, что у вас есть по мебели для офиса?» | **неясно** | Нет ни конкретики, ни объёма |
| «Ищу работу в вашей компании» | **нецелевой** | Запрос не про наш товар |
| «Сколько стоит продажа яблок оптом?» | **нецелевой** | Чужой товар |

В карточке есть поле **«Почему такой тип лида»** — туда попадает объяснение выбора.

Дополнительно сервер страхует от типичных сбоев модели:

- «целевой», но в заявке вообще нет данных → «неясно»;
- «целевой», но нет контакта → «контакт» добавляется в список «чего не хватает»;
- «неясно», но не указано, чего не хватает → список заполняется автоматически;
- «нецелевой» → список «чего не хватает» и вопросы очищаются: уточнять нечего.

## Если что-то не работает

| Сообщение | Что делать |
|---|---|
| «Не найден ключ API» | В файле `.env` пустая строка `PROXY_API_KEY`. Откройте `.env`, впишите ключ и перезапустите приложение |
| «Ключ API неверный или истёк» | Ключ скопирован с ошибкой (лишний пробел) или истёк. Создайте новый ключ в кабинете |
| «На балансе ProxyAPI недостаточно средств» | Пополните баланс в разделе «Биллинг» на [console.proxyapi.ru](https://console.proxyapi.ru) |
| «Модель не найдена на сервере ProxyAPI» | В `.env` указана модель, которой нет в каталоге. Проверьте список моделей на [proxyapi.ru/models](https://proxyapi.ru/models) |
| «Слишком много запросов к API» | Слишком часто нажимаете «Обработать». Подождите минуту |
| «AI-сервис не ответил за 60 секунд» | Проверьте интернет и баланс на ProxyAPI, попробуйте другую модель |
| «AI ответил не в формате JSON» | Разовое сбои: попробуйте ещё раз. Если повторяется — смените модель в `.env` |
| «Порт 8000 уже занят» | Приложение уже запущено в другом окне Терминала — закройте его. Либо смените порт в `.env`, например `PORT=8080`. Если порт занят чем-то другим (контейнером Docker, например), приложение само переключится на свободный и напишет об этом в окне Терминала |
| Открылась чужая страница вместо нашей | Порт занят другой программой, и вы открыли его адрес. Посмотрите в окне Терминала реальный порт приложения и откройте `http://127.0.0.1:<порт>` |
| Страница не открывается | Приложение ещё не запустилось. Откройте Терминал в папке проекта и запустите `python app.py`, затем перейдите на http://127.0.0.1:8000 |

## Как поменять настройки

Всё меняется в файле `.env` — правьте его и перезапускайте приложение (Ctrl + C, затем запуск снова).

| Что поменять | Как |
|---|---|
| Ключ | `PROXY_API_KEY=...` |
| Модель | `OPENAI_MODEL=...` — например `openai/gpt-6-1-sol` или `deepseek/deepseek-v4.1-flash`. Каталог: [proxyapi.ru/models](https://proxyapi.ru/models) |
| Описание компании | `COMPANY_DESCRIPTION=...` |
| Порт | `PORT=3001` |

### Где менять сами правила

Правила квалификации лежат в одном месте — в файле `ai.py`:

- блок `RULES` — текст инструкции для AI (включая процедуру определения типа лида
  и примеры разбора). Правьте его, если хотите изменить логику или добавить примеры;
- блок `CONFLICT_MARKERS` и `CONFLICT_COMBOS` — слова и сочетания, по которым заявка
  принудительно передаётся человеку;
- функция `_derive_lead_type` в файле `app.py` — правило вывода типа лида из ответов AI.

После правки перезапустите приложение (Ctrl + C, затем запуск снова).

## Что такое `.venv` и зачем он нужен

`.venv` — это папка с отдельной копией библиотек для этого проекта. Без неё установка
библиотек изменила бы настройки вашего основного Python и могла бы сломать другие программы.

Создаётся один раз командой `python3 -m venv .venv` и больше не нужна: при следующих запусках
скрипт видит папку и использует её. Если вдруг что-то сломалось, её можно просто удалить —
при следующем запуске создастся новая.

Команда `source .venv/bin/activate` — это «войти» в эту копию Python. Она нужна только
при ручном запуске; скрипт `start.command` делает это сам.

## Бонус: документация по API

Приложение запущено — откройте **http://127.0.0.1:8000/docs**.
Это готовая страница, где можно вручную отправить заявку в API и посмотреть ответ,
не пользуясь основной страницей. Там же описаны все маршруты.

Запрос к API — `POST /api/analyze` с телом:

```json
{
  "text": "Нужны 20 офисных столов и 40 кресел",
  "name": "Иван Петров",
  "phone": "+7 900 123-45-67",
  "email": "ivanov@officeline.ru"
}
```

Поля `name`, `phone`, `email` необязательны — приложение само соберёт из них текст заявки
и передаст AI вместе с `text`. Ответ содержит карточку, а также поля `llm_request`
(текст, который реально ушёл в модель, обезличенный) и `entities` (список найденных
типов персональных данных без значений).

Описание компании для программных вызовов можно передать явно в поле `company_description` —
если его не указать, приложение возьмёт описание из `.env`.
Веб-страница это поле не использует: она всегда работает с описанием из `.env`.

Ещё два маршрута:

- `POST /api/preview` с теми же полями формы: возвращает обезличенный текст и список
  найденных типов данных, но модель не вызывает. Его использует блок предпросмотра на странице.
- `GET /api/b24/check` — отчёт по настройке Битрикс24: работает ли вебхук, какие стадии
  и источники доступны, кто ответственный, какие чаты можно выбрать. Только чтение,
  ничего не создаёт.
- `POST /api/crm/send` — отправляет уже готовую карточку в CRM без повторного вызова AI.
  Используется кнопкой «Повторить отправку».

## Чего здесь сознательно нет

Объём MVP ограничен намеренно. Не сделано: CRM, база данных, регистрация пользователей,
подключение мессенджеров, автоматическая загрузка заявок из почты или CRM.

Данные нигде не сохраняются: заявка отправлена — карточка показана — и всё. История
обращений не ведётся.

---

## Безопасность: главное правило

**Ключ API лежит только в файле `.env` и больше нигде.**

- Никогда не вставляйте ключ в код, в текст заявки или в скриншот.
- Файл `.env` уже добавлен в `.gitignore` — при отправке проекта в интернет или в репозиторий
  он не попадёт туда.
- Если ключ случайно где-то засветился — отзовите его в кабинете ProxyAPI и создайте новый.

Одно уточнение про приватность: текст заявки уходит на серверы ProxyAPI (а оттуда — к
провайдеру модели). Если в заявках есть персональные данные, учитывайте это.
